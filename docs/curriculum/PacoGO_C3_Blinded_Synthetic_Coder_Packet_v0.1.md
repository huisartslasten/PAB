# PacoGO C3 — Blinded Synthetic Coder Packet v0.1

Status: Synthetic coding exercise / candidate anchors / not an approved canonical codebook
Branch: `refactor/professional-v1`

## IMPORTANT — BLINDED MATERIAL

This packet is for independent coding. It intentionally contains no suggested answers, adjudication decisions or case classifications. The separate adjudication key must not be shared with coders before their independent records have been completed and locked.

These are synthetic examples, not real learner observations. This exercise assesses whether the candidate distinctions and instructions are understandable. It cannot establish empirical learner validity or population-level coding reliability.

## 1. Instructions to coders

Code each case independently. Do not discuss cases with other coders before submitting and locking your record. Do not consult the adjudication key.

Use only the information stated in each case. Do not infer a learner's intention, reason for an action, knowledge state or cause of non-response when it is not observed.

For every target-specific assessment:
- code each dimension separately;
- cite the exact case detail supporting your judgement;
- use the uncertainty/not-coded options where justified;
- do not let correctness automatically determine evidence status, quality, independence or contradiction;
- do not treat a task mismatch as learner failure;
- do not treat missing process material as proof that reasoning was absent;
- record assistance as an observed event before making an independence judgement.

If a category boundary is unclear, record the uncertainty and explain what additional anchor or information you would need. Do not resolve ambiguity by inventing a rule.

## 2. Candidate dimensions and labels

These are candidate labels for this exercise only. They are not yet an approved canonical codebook.

### A. Task-instance alignment

Question: Did this exact task instance, as designed and administered, provide a defensible opportunity to observe the specified target?

- `ALIGNED`
- `PARTIALLY_ALIGNED`
- `MISALIGNED`
- `UNCLEAR`
- `NOT_ASSESSED`

### B. Response-to-target relation

Question: How is this particular response/process related to the specified target?

- `DIRECT`
- `PARTIAL`
- `INDIRECT`
- `NONE`
- `INDETERMINATE`
- `NOT_CODED`

This is a relation judgement, not a demonstration judgement.

### C. Evidence status

Question: Does the available material demonstrate the evidence required by this target?

- `PRESENT`
- `ABSENT`
- `INDETERMINATE`
- `NOT_CODED`
- `NOT_APPLICABLE`

Use `ABSENT` only when relevant material was available and inspected and the required evidence was not demonstrated under a defensible, pre-specified protocol. `NOT_CODED` means no coding judgement has yet been made. `INDETERMINATE` means the material was inspected but does not support a defensible conclusion. `NOT_APPLICABLE` means the dimension/assessment does not apply under the task/target protocol.

### D. Objective performance

Candidate labels:
- `CORRECT`
- `INCORRECT`
- `MIXED`
- `NOT_OBSERVED`
- `NOT_SCORABLE`

Record only what can be scored under the information supplied. Do not infer target mastery.

### E. Raw process availability

Candidate labels:
- `COLLECTED`
- `NOT_COLLECTED`
- `TECHNICAL_FAILURE`
- `OBSERVER_UNABLE`
- `NOT_APPLICABLE`

Record `NO_RESPONSE` as a raw response event where it occurs. It is not itself an evidence-status label.

### F. Assistance exposure

Describe the assistance event actually stated in the case. Record:
- whether assistance is stated;
- its stated source/content/timing, if supplied;
- whether it appears target-relevant, with a short rationale;
- what remains unknown.

Do not convert assistance directly into contradiction or evidence absence.

### G. Target-specific independence

Candidate labels:
- `INDEPENDENT`
- `PROMPTED`
- `DEPENDENT`
- `UNKNOWN`

Judge separately for each target. The exact boundary between `PROMPTED` and `DEPENDENT` is intentionally under review. Explain your reasoning rather than guessing a hidden rule.

### H. Target-specific contradiction

Candidate labels:
- `PRESENT`
- `ABSENT`
- `INDETERMINATE`
- `NOT_CODED`
- `NOT_APPLICABLE`

A `PRESENT` judgement requires the specific observed material, the target-level interpretation it conflicts with, and why the conflict is material. Incorrectness, missing process, prompting or task mismatch alone does not automatically establish contradiction.

## 4. Synthetic cases

### Case A — selection and explanation

A learner completes a task that was designed to assess both recognition and a specified reasoning target. The learner selects the expected option and gives an explanation that is coherent with the required reasoning. The response and explanation are captured. No prompt, hint or other assistance is delivered.

Code the recognition target and the reasoning target as two separate target-specific records.

### Case B — selection and conflicting explanation

A learner completes a task designed to assess recognition and a specified reasoning target. The learner selects the expected option. The captured explanation conflicts with the reasoning required by the reasoning target. No prompt, hint or other assistance is delivered.

Code the recognition target and the reasoning target as two separate target-specific records. Explain whether and how the same observed material bears differently on the two targets.

### Case C — task does not assess intended target

A task is administered with the stated intention of assessing a particular target. On inspection, the item does not provide a defensible opportunity to observe that target. The learner's answer to the item is incorrect. The answer itself is available.

Code the intended target. Distinguish what can be said about the item response from what can be said about the intended target.

### Case D — correct response after strategy prompt

A task suitable for the specified target is administered. The learner gives the expected correct answer after receiving a prompt that supplies the strategy required by the target. The prompt and its timing are captured. No further process explanation is available.

Code the target. Describe the assistance event before judging independence. State any uncertainty about the category boundary.

### Case E — correct selection, process not collected

A learner completes a task with a correct selection. The task can provide an evidence opportunity for a recognition target. A separate reasoning target requires inspectable process evidence, but no explanation or process record was collected. No assistance is recorded.

Code the recognition target and the reasoning target as two separate target-specific records. Do not infer unrecorded reasoning.

### Case F — no response

A learner is presented with a task intended to assess a specified target. No response is recorded before the observation ends. The available record does not establish why no response occurred. No further contextual or technical information is available.

Code the target. Record the raw response event separately from your evidence judgement. Do not infer the cause.

## 5. Independent submission and lock

Each coder should submit their completed records independently to the study coordinator. The coordinator should preserve the original records unchanged and record the submission/lock time before any coder discussion.

Do not overwrite an initial judgement after discussion. Any correction, recoding or adjudication must be a new linked record with coder, date, reason and version information.

## 6. Scope and limitations

This packet is a synthetic feasibility instrument. It does not:
- define a final canonical codebook;
- choose a quality scale;
- establish a reliability statistic or threshold;
- validate curriculum claims, mastery or next-action decisions;
- authorize runtime, schema, persistence or Supabase changes.

The exercise can reveal unclear instructions, category overlap and disagreement patterns in these examples. It cannot establish that the same coding rules are valid for real learner data.
