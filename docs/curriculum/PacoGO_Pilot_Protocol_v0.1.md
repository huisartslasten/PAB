# PacoGO Curriculum — Pilot Protocol v0.1

Date: 2026-11-02  
Status: Candidate protocol / [O]  
Purpose: C1 Pilot Design + initial C2/C3 operationalization.

## 1. Purpose of the pilot

The first empirical study is a **measurement-development pilot**, not a proof that the PacoGO curriculum is correct or effective.

The pilot asks whether PacoGO can collect and code evidence that is:

- observable;
- reproducible;
- claim-linked;
- distinguishable across candidate developments;
- robust to controlled task variation;
- sufficiently documented to support later empirical tests.

This ordering follows a basic measurement principle: before stronger validity or longitudinal claims are tested, the intended construct and its measurement/evidence process must be sufficiently clear. The Standards for Educational and Psychological Testing provide the general testing framework, while measurement-development methodologies emphasize establishing what is being measured before interpreting later properties. citeturn758549search1turn758549search38

## 2. Scope

The pilot uses the existing representative seed curriculum:

- A1 — Getallen representeren en verbinden
- B1 — Optellen
- FR2 — Breukequivalentie herkennen en gebruiken

These are **research targets**, not validated curriculum truths. Their current registry status remains `Candidate`.

## 3. Pre-specified hypotheses

Each tested claim must be copied into the pilot record before learner data are interpreted.

For each claim specify:

1. claim ID and exact text;
2. intended development;
3. evidence targets;
4. task models;
5. expected observable evidence;
6. plausible alternative explanations;
7. observations that would contradict the claim;
8. criteria for considering the evidence interpretable;
9. planned analysis;
10. revision/stopping rule.

The pilot must not change these definitions merely because early data are inconvenient. Changes create a new protocol version.

## 4. Sampling logic

The pilot is deliberately **criterion-driven rather than convenience-driven**.

The protocol must record:

- target learner population;
- inclusion criteria;
- exclusion criteria;
- relevant language/context variables;
- recruitment source;
- number approached, enrolled and retained;
- missing observations and reasons;
- testing occasions.

No universal sample-size number is embedded in this protocol. Required sample size depends on the specific claim, design, measurement property and planned analysis and must be justified before the confirmatory phase.

## 5. Observation unit

The atomic observation is:

`Student × Time × Task × Response × Evidence`

Every observation preserves the chain:

`curriculum version → skill → development → claim → evidence target → task model → task → performance → evidence`

Where available, preserve:

- response;
- response time;
- attempts;
- hints/prompts;
- representation used;
- strategy/process indicators;
- confidence/explanation where explicitly collected;
- contextual variables;
- evaluator/coder identity;
- coding version.

## 6. Task variation

A pilot must not test a development claim with one fixed task form only.

Variation should be pre-specified along relevant dimensions such as:

- representation;
- numerical magnitude;
- surface/context;
- response format;
- degree of explicit prompting;
- transfer/context change.

The purpose is not to make tasks arbitrarily harder. It is to test whether the intended evidence survives meaningful variation rather than merely reproducing a memorized task form.

## 7. Response-process evidence

Where the claim depends on reasoning rather than an answer alone, the pilot should collect process evidence sufficient to distinguish plausible explanations.

Examples:

- explanation of how an answer was obtained;
- selected representation;
- strategy choice;
- correction after error;
- independent choice versus prompted choice.

A correct answer without the required process evidence must not automatically count as support for a higher developmental claim.

## 8. Evidence coding

Coders work from the coding manual, not from the desired developmental outcome.

Each observation receives, where applicable:

- evidence target match;
- evidence present/absent/indeterminate;
- quality;
- independence;
- variation key;
- contradiction flag;
- alternative explanation;
- coder note.

The coding unit is evidence, not a final developmental label.

## 9. Rater procedure

For observations requiring judgment:

1. train coders on the written codebook;
2. code a calibration set;
3. record disagreements;
4. resolve disagreements using the predefined procedure;
5. freeze the coding rule before confirmatory coding;
6. retain original and resolved coding records.

Agreement statistics are not interpreted as proof of construct validity; they establish reproducibility of the coding procedure.

## 10. Planned analysis sequence

The pilot analysis is sequential:

### Phase A — Data integrity
Check provenance, missingness, task identity, curriculum version and coding completeness.

### Phase B — Evidence quality
Determine whether observations contain the evidence required by each target.

### Phase C — Development distinguishability
Examine whether candidate developments generate distinguishable evidence patterns rather than simply different task difficulty levels.

### Phase D — Alternative explanations
Test whether observed patterns could plausibly arise from memorization, familiarity, language, prompting, general task skill, or another non-target explanation.

### Phase E — Model comparison
Where data permit, compare the candidate developmental interpretation against simpler or alternative explanations.

### Phase F — Revision
Classify each claim as:

- retain as Candidate for further study;
- modify operationalization;
- narrow scope;
- split/merge construct;
- reject current formulation.

The pilot does not promote claims to `Supported` merely because the data look promising.

## 11. Predefined stopping/revision rules

Stop or revise the pilot component when:

- the intended evidence cannot be observed reliably;
- coders cannot apply the rule reproducibly;
- a task systematically measures an unintended feature;
- alternative explanations cannot be separated with the current design;
- the candidate development distinction is not empirically distinguishable;
- critical provenance is missing.

A failed pilot component is a useful scientific result and must remain documented.

## 12. Relation to C1-C3

- **C1:** protocol, hypotheses, scope, task variation, sampling, analysis and revision rules are pre-specified.
- **C2:** the pilot data schema preserves student/task/time/context/provenance.
- **C3:** evidence coding is rule-based, versioned and auditable.

C4-C10 are not considered completed by writing this protocol.

## 13. Scientific status

This document is a PacoGO research design artifact `[O]` informed by established measurement/testing principles. It does not constitute empirical evidence for A1, B1 or FR2.
