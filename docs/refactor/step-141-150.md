## Verified editor-save boundary

The editor flow is now represented as three separate responsibilities:

1. `editor-model.js`
   - builds the lesson payload from `student`, `subject`, `title`, and `type`;
   - builds the editor model;
   - keeps draft validation separate from persistence.

2. `editor-items.js`
   - builds deterministic items per supported lesson type;
   - filters non-meaningful rows;
   - assigns deterministic `sort_order` values.

3. `editor-service.js`
   - existing lesson: update lesson, then replace all lesson items;
   - new lesson: create lesson, obtain its id, then replace/insert lesson items through the lesson service.

4. `editor-controller.js`
   - converts raw editor input to the domain payload/items;
   - validates before persistence;
   - calls the editor service;
   - refreshes lessons and returns the saved editor model.

## Important correction

The editor service previously bypassed `createLessonService` for new lessons and called Supabase directly. That duplicated the persistence boundary. It now routes new-lesson creation through `lesson-service.js`, matching the existing service boundary used by update and item replacement.

The editor model API was also aligned with the controller (`buildLessonPayload` and `buildEditorModel`). This was a real consistency issue discovered during the parity pass, not a runtime redesign.
