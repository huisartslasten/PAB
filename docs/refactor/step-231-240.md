## Test-history database contract
The test-history schema was verified directly from the V4.78 backup branch migration:
`supabase/migrations/20260929140000_create_test_history.sql`

### `test_attempts`
Verified columns:
- `id`
- `lesson_id`
- `student`
- `score`
- `total_questions`
- `started_at`
- `completed_at`
- `is_test`
- `created_at`

Relevant constraints:
- `score >= 0`
- `total_questions >= 0`
- `score <= total_questions`

The important parity implication is that `score` is a count of correct answers, not a percentage/1–10 grade. The 1–10 grade belongs to the result presentation model and must not be written into the `score` column.

### `test_attempt_answers`
Verified columns:
- `id`
- `attempt_id`
- `question_order`
- `question`
- `expected_answer`
- `given_answer`
- `is_correct`
- `question_type`
- `answered_at`

`attempt_id` references `test_attempts(id)` and answer rows are ordered by `question_order`.

## Important remaining parity item
The schema contract is now verified, but the exact historical V4.78 runtime call that assembles these rows at test completion should still be reconstructed before runtime wiring. In particular, do not invent how `question_type`, per-answer timestamps, or any lesson/player object is transformed at the historical call site if the source does not establish it.
