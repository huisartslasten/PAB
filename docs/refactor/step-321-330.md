## 321–330 — Lesson write orchestration boundary

The exact V4.78 `saveLesson()` contract was reconstructed from the authoritative TEST V4.78 `index.html` backup and extracted into a tested orchestration boundary.

### Production boundary

`src/features/lessons/lesson-write-service.js`

The new service owns only persistence orchestration:

1. Build the exact `lessons` payload used by the legacy editor.
2. For a new lesson, insert the lesson and obtain its id.
3. Replace `lesson_items` using the existing lesson service.
4. For an existing lesson, update the lesson by id first.
5. Then delete existing `lesson_items` and insert the replacement rows.
6. Preserve the existing item normalization: `hint`, `min_words`, `required_terms`.

It performs no DOM work, navigation, AI calls, or UI decisions.

## Important parity boundary

The legacy `saveLesson()` call-site in `index.html` has **not** been replaced yet. This checkpoint extracts and tests the persistence contract only. Runtime wiring remains a separate gate.

The historical implementation also does not perform a rollback when a newly created lesson's item insert fails; this boundary intentionally does not introduce such new behavior.
