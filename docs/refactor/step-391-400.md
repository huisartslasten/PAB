## Source-proven V4.78 contract
The authoritative V4.78 `saveLesson()` runs the spelling check only when the lesson type is exactly `dictation`, after required-field validation and before lesson persistence.

For a dictation lesson:

1. The UI shows a temporary `AI controleert de spelling van je dicteewoorden...` status.
2. `checkDictationSpelling()` builds entries from the dictation editor rows, using one-based row numbers and non-empty answer values.
3. It invokes Supabase function `check-dictation-spelling-v1` with `{ entries, subject }`.
4. A returned `issues` array is a warning only. V4.78 does not modify the entered words and explicitly allows the parent to ignore the warning.
5. A checker failure is also non-blocking: V4.78 catches the failure, displays `AI-spellingscontrole niet beschikbaar. De les wordt toch opgeslagen; de ouder blijft verantwoordelijk.`, and continues to persistence.
6. A missing checker response produces `Geen antwoord van de spellingscontrole.` and is handled by the same non-blocking save path.
7. Non-dictation lesson types do not execute this spelling-check gate.

## Refactor boundary

- `src/features/lessons/dictation-spellcheck.js`

It contains no DOM access, Supabase access, UI rendering, navigation, or state mutation. The actual checker is injected.

The boundary exposes:

- `runDictationSpellcheck()` — invokes the injected checker and returns normalized issues;
- `buildDictationSpellcheckEntries()` — creates the V4.78 row-numbered, non-empty entry payload;
- `buildDictationWarning()` — reconstructs the V4.78 warning content;

The boundary deliberately does not decide whether the lesson may be saved. Checker failures are propagated so the future save orchestration can catch them and continue exactly as V4.78 does.
