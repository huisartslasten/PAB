## Source-proven V4.78 contract
The authoritative V4.78 `saveLesson()` performs the test-calendar side effect only after the lesson write succeeds, `loadLessons()` completes, and the saved lesson can be found again by id.

The exact behavior is:

- If `testDate` is truthy, upsert a local test-calendar entry for the saved lesson and current student.
- If `testDate` is empty, remove the local test-calendar entry for the saved lesson and current student.
- The calendar entry uses the existing id when the same `lessonId + student` pair already exists.
- A new entry receives `Date.now().toString()` as its id.
- `lessonId` is stored as a number.
- The entry stores `student`, `subject`, `title`, and `date` from the saved lesson/current save state.
- Matching is by numeric `lessonId` and exact `student`.
- Calendar rendering and sidebar refresh happen only after this side effect.
- The success message is selected from the presence of `testDate`:
  - `Les opgeslagen en toetsdatum toegevoegd.`
  - `Les opgeslagen.`
- If the reloaded lesson cannot be found, V4.78 skips the calendar mutation and proceeds to the render/refresh/success path.

The underlying V4.78 helpers are `getTestCalendar()`, `saveTestCalendar()`, `upsertTestDate()`, and `removeTestDate()`, all backed by localStorage. The extracted boundary intentionally does not perform localStorage or UI work.

## Refactor boundary
Added:

- `src/features/lessons/lesson-test-calendar.js`

The module is pure. It models the V4.78 add/update/remove behavior without DOM, localStorage, rendering, navigation, or state mutation.

It exposes:

- `upsertLessonTestDate()` — exact V4.78 upsert model;
- `removeLessonTestDate()` — exact V4.78 removal model;
- `syncLessonTestDate()` — selects upsert vs removal from the presence of `date`.

The id generator is injected so the boundary remains deterministic and testable while preserving the V4.78 default of `Date.now().toString()`.
