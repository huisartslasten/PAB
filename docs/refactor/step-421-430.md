## Source-proven orchestration
The authoritative V4.78 `saveLesson()` sequence remains:

1. parent authentication;
2. DOM editor-state extraction;
3. canonical subvak resolution;
4. `collectItems()`;
5. required-field/item validation;
6. dictation-only spelling check;
7. lesson create/update;
8. lesson-item write;
9. persistence failure stops the save;
10. post-save state assignment and reload;
11. saved-lesson lookup and test-calendar add/update/remove;
12. calendar/sidebar refresh;
13. success message.

The refactor now has independent boundaries for the core save decisions:

**validation → optional dictation spelling check → deterministic lesson/item write → reload/post-save resolution → test-calendar action**

The remaining application responsibilities stay outside the coordinator: authentication, DOM extraction, canonical subvak lookup, actual `loadLessons()` implementation, state mutation, rendering, sidebar refresh, success/error UI, navigation, and runtime sequencing.

## New boundary
Added:

- `src/features/lessons/lesson-save-coordinator.js`

`executeLessonSaveCore()` composes the proven contracts through injected functions. It deliberately has no DOM, Supabase client, localStorage, UI, navigation, or application-state access.

Important V4.78 semantics locked into the coordinator:

- item collection occurs before validation;
- invalid validation stops before dictation checking and persistence;
- dictation checking occurs only for `type === 'dictation'`;
- spelling warnings do not block persistence;
- spelling-check failure is converted to the exact V4.78 unavailable message and does not block persistence;
- persistence failure stops before reload/calendar sync;
- reload occurs before post-persistence outcome resolution;
- calendar sync follows the resolved V4.78 `upsert`/`remove` decision.

The coordinator intentionally does **not** display the final success message or refresh sidebars. Those remain runtime/UI responsibilities.
