# PacoGO refactor — checkpoint 511–520

## Scope
Controlled TEST runtime wiring for the V4.78 lesson-save flow.

## What was verified from source
- `index.html` on `refactor/professional-v1` is still the authoritative V4.78 blob `de4ebcc75b1b333cc985936c86f7c654c818be24`.
- The legacy page is a classic script environment.
- `photo-storage.js` is also a classic script and already reads the V4.78 lexical application bindings directly.
- `lesson-save-runtime-entry.js` is an ES module and therefore must not assume those classic-script lexical bindings are module-visible.

## Runtime bridge correction
The runtime boundary was corrected so the ES module receives an explicit V4.78 runtime bridge from the classic-script boundary.

`photo-storage.js` builds a bridge with live getters/setters for the V4.78 application dependencies, including `document`, Supabase `db`, mutable lesson state, parent/session data, lesson collections, editor helpers, persistence/calendar helpers, and UI refresh functions.

`lesson-save-runtime-entry.js` requires that bridge explicitly and no longer resolves classic-script lexical bindings from ES-module scope.

## Explicit bootstrap boundary
The remaining bootstrap problem was identified as an architectural boundary issue rather than a timeout/fallback problem. A dedicated `lesson-save-runtime-bootstrap.js` boundary now owns the module-loading contract:

- validates the injected V4.78 runtime bridge and target;
- loads the runtime entry explicitly;
- verifies the installer contract;
- installs the runtime entry exactly once through the existing installer;
- publishes `window.pacoGOLessonSaveRuntimeReady` as the explicit readiness contract;
- propagates module/installer failures instead of falling back to legacy save execution.

`photo-storage.js` now enters through this bootstrap boundary rather than directly chaining the runtime-entry installer.

These tests are source-level regression coverage only. They have **not** been executed in the available environment, so no test pass is claimed.

## Status
**Checkpoint 511–520 remains open.** The architectural bootstrap seam is now explicit, but a real browser execution of the V4.78 save path is still required before the legacy `saveLesson()` implementation can be removed or the checkpoint can be declared complete. In particular, the readiness contract must be validated against the real page's save invocation timing; no timeout or compatibility fallback is permitted.
