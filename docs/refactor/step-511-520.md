# PacoGO refactor — checkpoint 511–520

## Scope
Controlled TEST runtime wiring for the V4.78 lesson-save flow.

## What was verified from source
- `index.html` on `refactor/professional-v1` is still the authoritative V4.78 blob `de4ebcc75b1b333cc985936c86f7c654c818be24`.
- The actual V4.78 save buttons still invoke the global `saveLesson()` entry from inline handlers.
- The page is a classic script environment; the final `<script src="photo-storage.js">` executes the runtime bridge after the legacy application code has been defined.
- `lesson-save-runtime-entry.js` is an ES module and therefore must not assume classic-script lexical bindings are module-visible.

## Runtime bridge correction
The runtime boundary was corrected so the ES module receives an explicit V4.78 runtime bridge from the classic-script boundary.

`photo-storage.js` builds a bridge with live getters/setters for the V4.78 application dependencies, including `document`, Supabase `db`, mutable lesson state, parent/session data, lesson collections, editor helpers, persistence/calendar helpers, and UI refresh functions.

`lesson-save-runtime-entry.js` requires that bridge explicitly and no longer resolves classic-script lexical bindings from ES-module scope.

## Explicit bootstrap boundary
The remaining bootstrap problem was identified as an architectural boundary issue rather than a timeout/fallback problem. A dedicated `lesson-save-runtime-bootstrap.js` boundary now owns the module-loading contract:

- validates the injected V4.78 runtime bridge and target;
- loads the runtime entry explicitly;
- verifies the installer contract;
- installs the runtime entry exactly once through the existing installer;
- verifies that the installer actually produced a callable `saveLesson` entry;
- publishes `window.pacoGOLessonSaveRuntimeReady` as the explicit readiness contract;
- returns the installed runtime entry from that readiness promise;
- propagates module/installer failures instead of falling back to legacy save execution.

### Save invocation timing boundary
Source verification showed that the legacy page invokes `saveLesson()` directly from inline editor button handlers. Waiting for the dynamic ES module to finish loading before defining `saveLesson` would therefore leave a real startup race.

The correct architectural solution is now an explicit synchronous runtime facade at the classic-script boundary in `photo-storage.js`:

1. the facade is defined immediately when `photo-storage.js` executes;
2. the facade awaits the single bootstrap readiness promise;
3. once ready, it invokes the installed refactored runtime entry;
4. if bootstrap/module installation fails, the promise rejects and no legacy save fallback runs.

This is a deliberate boundary contract, not a timeout, retry, compatibility shim, or patch to the legacy save implementation.

The bootstrap module itself does not invent fallback behavior. It returns the callable runtime entry installed by `lesson-save-runtime-entry.js`, so the facade has an unambiguous target after readiness.
