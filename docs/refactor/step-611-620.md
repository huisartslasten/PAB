# Checkpoint 611–620 — Lesson ordering runtime boundary

## Scope
Extract the V4.78 lesson ordering ownership from `index.html` into a deterministic service/runtime boundary while preserving behavior exactly.

## Authoritative V4.78 contract
Source: `backup-test-v478-before-professional-rewrite/index.html`, blob `de4ebcc75b1b333cc985936c86f7c654c818be24`.

The legacy contract was:
- remote order comes from `lesson_order` filtered by `student` and `subject`, ordered by `position` ascending;
- if remote rows exist, their lesson IDs determine rank;
- otherwise the local-storage order `pacogo-lesson-order-<student>-<subject>` is used;
- unknown lessons sort after ranked lessons and then by numeric lesson ID;
- saving always attempts local-storage persistence first;
- remote persistence is skipped when student/subject is missing, there are no IDs, or the parent is not logged in;
- remote save deletes the existing student/subject rows, then inserts `{student, subject, lesson_id, position}` rows;
- database errors propagate from the remote write boundary.

## New boundary
- `src/features/lessons/lesson-order-service.js`
  - remote/local order persistence;
  - deterministic order application;
  - no DOM dependencies.
- `src/features/lessons/lesson-order-runtime.js`
  - runtime orchestration for read/apply and save flows.
- `src/features/lessons/lesson-order-runtime-entry.js`
  - explicit runtime bridge validation and public runtime handlers.
- `src/features/lessons/lesson-order-runtime-bootstrap.js`
  - dynamic bootstrap/readiness boundary.

## Runtime wiring
`index.html` now contains only thin readiness-backed facades for `getOrderedLessons()` and `saveLessonOrder()`. The legacy lesson-order implementation, local-storage helper, and direct `lesson_order` Supabase calls were removed from the monolith.

A one-time migration workflow was used for the controlled legacy removal and then deleted; it is not part of the permanent runtime architecture.
